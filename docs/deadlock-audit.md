# 事务与死锁审计（2026-11-17）

本次检查覆盖 Java 的事务注解、程序化事务、显式数据库锁、JVM 同步与等待入口，
并沿调用链检查 mapper SQL、外键、唯一约束、TimescaleDB 分块写入，以及 Flarum 扩展的事务入口。
下面区分有明确锁顺序冲突的修复与减少持锁时间的调整。静态审计和并发回归不能证明任意生产负载下绝无死锁。

## 已修复的锁顺序问题

| 路径 | 原来的等待环或风险 | 处理方式 |
| --- | --- | --- |
| 生涯统计 | 一份上报跨越 500 条边界后重新访问较小的用户或日期；另一份上报可按相反顺序持有累计行 | 先取得去重后的增量，再对整份上报的累计流量、生涯日计数和每日流量分别排序、分批写入；保持每次 SQL 最多 500 条和同事务原子性 |
| 生涯活动时间 | 同一用户的不同应用按不同种子顺序写活动时间行 | 整份上报按种子及会话顺序排列；SQL 明确声明检查点、事件、活动时间之间的依赖 |
| 心跳、Swarm、客户端发现 | 请求顺序或 HashMap 顺序导致同一组唯一键反向争用 | 写入前按稳定键顺序排列 |
| AI 审核 | 正常完成先更新内容再更新任务；失败和补审原来先更新任务再更新内容 | 统一为内容、修订、任务的顺序；补审每条内容一个短事务，全量重新审核每条内容一个原子语句 |
| 通知与配置 | 退订列表、BTN 配置和首页模块配置可按请求顺序更新同一组行 | 固定类别、配置键、模块的写入顺序 |
| 用户资料与外键 | `FOR UPDATE` 与子表插入的外键检查冲突，随后用户更新可能形成锁升级等待环 | 不修改用户主键的资料读取使用 `FOR NO KEY UPDATE`；保留角色、绑定等读改写的一致性 |
| 管理员积分调整 | 显式读取并锁定用户行，增加与外键写入冲突的机会 | 原子条件更新并 `RETURNING` 新余额；数据库检查非负和 bigint 上限，审计前后余额来自本次更新 |
| 会员身份补授 | 批量 UPDATE 的用户行锁顺序不受输入列表约束，可能与积分结算相反 | 每位用户一个自动提交的条件更新，不跨用户保留行锁 |
| 注销和管理删除 | 删除顺序与写入顺序不一致；两位用户可共享联系邮件记录 | 调整统计删除顺序，共享邮件按 ID 更新；管理删除先删除用户再清理关联记录 |
| 汇率缓存 | 持有刷新 monitor 的线程可能等待另一笔事务中的汇率行；该事务再次刷新时又等待 monitor | 汇率缓存写入独立自动提交，不把缓存行锁带回会员业务事务 |

PostgreSQL 的锁会保留到事务结束，因此只在某一个批次内部排序不足以约束整笔事务。
可写 CTE 的文本先后也不等于执行先后，必须建立实际数据依赖。
依据：[PostgreSQL 18 锁与死锁](https://www.postgresql.org/docs/18/explicit-locking.html)、
[可写 CTE 的执行规则](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-MODIFYING)。

## 缩短的事务边界

- Swarm 和封禁上报先完成校验、种子注册、GeoIP 查询及对象准备，再进入数据库写入事务。
  种子是独立共享字典，注册成功后不随某次上报回滚；缓存只会引用已经提交的种子。
  原始记录、去重状态、生涯累计和相关统计仍然一起提交或回滚。
- 移除心跳 Redis 入队上的接口事务，以及应用的单条增删改、只读 BTN 允许列表生成等不需要外层事务的入口。
- 心跳和 Swarm 清理使用一次 SQL 领取并删除最多 1000 条过期记录，每次调度最多 20 批。
  每批自动提交，`SKIP LOCKED` 跳过正在更新的记录，下次调度再处理；不再先读 ID 后无条件删除。
- 联系邮件只在检查额度、预留发送记录时开启事务，提交后同步调用 SMTP。
  明确发送失败会删除预留记录；进程在发送期间退出时，记录保留并占用当日额度，避免重发或突破限额。
  SMTP 与数据库之间不承诺分布式原子提交。
- 爱发电绑定在外部订单查询、缓存与汇率换算完成后，才以短事务写入两份绑定。
  解绑的两份记录仍需一起提交。授权导入先换算金额，再获取现有导入协调锁。
- 会员金额重算每次读 200 条，各行独立更新，网络换算期间不持有先前交易行的锁。
  更新时检查原金额与币种；已被同步修改的行跳过，避免覆盖较新的金额。

## 保留的协调与原子性

没有新增数据库表或 Java 手动锁。积分结算、去重及累计、绑定、注销和需要多步原子性的配置写入仍保留事务。
导出池准入、任务领取、发送额度、授权导入和 Flyway 启动协调仍需要现有串行化边界。
`SKIP LOCKED` 属于语句内的领取机制，锁由事务自动释放，没有额外手动解锁流程。
只读 MyBatis Cursor 分析任务依赖有效的会话/事务生命周期，未机械删除其事务注解。
已有 IP 标志发布和积分账本分块写入的顺序修复继续保留。

全量补审和金额重算改为逐项提交，任务中途失败不会撤销已经完成的项；可以再次执行。
本次没有修改历史 Flyway 文件，也不要求数据回填。
